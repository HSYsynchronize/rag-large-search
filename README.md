# RAG 大规模对话检索系统

把 1 万条模拟对话（2 万条记忆条目）存进向量库，用**四种**检索引擎做对比实验，验证近似检索（ANN）在大规模数据下的真实优势与取舍。

核心结论：**16K 向量下，FAISS IVF 比 NumPy 暴力检索快 740 倍，比 FAISS Flat 快 16 倍；HNSW 又比 IVF 快 4.9 倍，但建索引慢 8 倍。**

---

## 这个项目在做什么

一个 RAG 记忆系统的规模化验证：当对话记录从 10 条涨到 1 万条，暴力检索还能不能用？近似检索到底该怎么选？

答案是：NumPy 暴力检索在 16K 向量时要 543ms，10 万条预计 3.3 秒，不可接受。而 IVF 把线性复杂度降到亚线性，16K 时只要 0.73ms；HNSW 更进一步，但要付出建索引的代价。

---

## 实验结果

### 引擎对比总览（16K 向量，去重后数据）

| 检索引擎 | 2K 向量 | 16K 向量 | 增长 | 召回@10 | 索引体积 | 构建耗时 |
|---------|---------|---------|------|---------|---------|---------|
| NumPy 暴力检索 | 70ms | 543ms | 7.8x | 100% | — | — |
| FAISS Flat（精确） | 0.76ms | 11.5ms | 15x | 100% | 65.0MB | 0.02s |
| FAISS IVF（近似） | 0.69ms | 0.73ms | 1.06x | 99.2% | 65.8MB | 0.4s |
| **FAISS HNSW（近似）** | — | **0.13ms** | — | 98.8%* | 69.3MB | 3.4s |

\* 召回率 98.8% 是评测假象，实际无损——见下文"并列分数"分析。

### 精度验证（100 条随机查询，原始实验）

| 指标 | 结果 |
|------|------|
| top-1 一致率 | 100/100 (100%) |
| top-5 重叠率 | 5.0/5 (100%) |
| top-1 分数差异 | 0.0000 |

**关键工程判断**：数据量 < 1 万条时 Flat 就够用（IVF 优势不明显）；> 1 万条时 IVF 的意义才显现——它不是"稍微快一点"，而是把复杂度从线性变成亚线性。

---

## IVF vs HNSW：同是近似检索，该怎么选

这是本项目第二轮实验的核心问题。两者都用近似算法降低计算量，但走的是完全不同的路：

- **IVF（聚类式）**：先把向量聚成若干簇，查询时只扫最近的几个簇（本项目扫 12%）。降低的是**要计算的向量数**。
- **HNSW（图式）**：把所有向量组织成分层邻近图，查询时在图上贪心地跳向最近的邻居。降低的是**要访问的步数**。

### 默认参数下的正面对比

| 指标 | IVF | HNSW | 结论 |
|------|-----|------|------|
| 检索延迟 | 0.626ms | **0.127ms** | HNSW 快 **4.9 倍** |
| 召回@10 | 99.2% | 98.8% | 基本持平（差异为评测假象） |
| 索引体积 | 65.8MB | 69.3MB | HNSW 多占 5% |
| 构建耗时 | 0.43s | 3.38s | **HNSW 慢 8 倍** |

### 参数扫描：两者的"精度-速度旋钮"

**IVF 的旋钮是 nprobe**（扫描多少个簇）——影响很大，是真实的质量取舍：

| nprobe | 扫描比例 | 延迟 | 召回@10 |
|--------|---------|------|---------|
| 1 | 0.6% | 0.049ms | **89.45%** |
| 2 | 1.2% | 0.069ms | 94.55% |
| 4 | 2.4% | 0.114ms | 97.55% |
| 8 | 4.8% | 0.224ms | 98.25% |
| 16 | 9.6% | 0.471ms | 99.05% |
| 32 | 19.3% | 0.953ms | 99.45% |
| 64 | 38.6% | 1.862ms | 99.55% |

**HNSW 的旋钮是 efSearch**（搜索宽度）——在本数据集上几乎无效，因为瓶颈不在搜索：

| efSearch | 延迟 | 召回@10 |
|----------|------|---------|
| 16 | 0.046ms | 98.75% |
| 64 | 0.129ms | 98.80% |
| 256 | 0.547ms | 98.80% |

**HNSW 的 M**（图连通度）同样无效，排除了"图质量不足"的可能：

| M | 构建耗时 | 索引体积 | 召回@10 |
|---|---------|---------|---------|
| 8 | 2.48s | 66.3MB | 98.80% |
| 32 | 2.98s | 69.3MB | 98.80% |
| 64 | 3.07s | 73.4MB | 98.95% |

### 结论：怎么选

| 场景 | 选择 | 理由 |
|------|------|------|
| 数据会频繁增删、要求最高召回 | **IVF** | nprobe 可调、构建快 8 倍、召回可逼近 100% |
| 查询延迟敏感、索引一次性构建 | **HNSW** | 快 4.9 倍；建索引的一次性成本可摊销 |
| 数据 < 1 万条 | **Flat** | 亚毫秒级，近似检索的复杂度没有意义 |

**一句话**：HNSW 用"建索引慢 8 倍"换"查询快 4.9 倍"。索引只构建一次、查询千万次，所以这个交换通常是划算的——但如果数据每天都在变，IVF 更实际。

## 最值得说的一节：两个"假象"

本实验最有价值的产出不是性能数字，而是**两个差点被误读为"精度损失"的现象**。它们的根因是同一个。

### 假象一：top-1 一致率只有 6%（第一轮实验）

扩大到 100 条随机查询验证时，IVF 与 NumPy 的 top-1 一致率只有 6%。排查后发现：数据集重复率高达 94.2%（1 万条只有 582 条唯一），两者找到了分数相同的好结果，只是选了不同副本。

### 假象二：HNSW 召回率"卡"在 98.8%（第二轮实验）

测 HNSW 时召回率 98.8%，一开始怀疑是图质量不足。做了两组对照：
- `efSearch` 从 16 扫到 256 → 召回率纹丝不动 → 排除"搜索不充分"
- `M` 从 8 扫到 64 → 召回率纹丝不动 → 排除"图连通度不足"

两次都无效，说明瓶颈不在索引参数。于是转向验证数据本身：

| 证据 | 数值 | 说明 |
|------|------|------|
| top-1 分数平均差异 | 0.00000011 | 纯浮点误差量级，**不是精度损失** |
| top-10 末端分数差异 | 0.00000010 | 同上 |
| 分数集合相同但条目不同 | 15/200 条 | 并列分数导致 ID 不确定 |

**结论：HNSW 找到的结果分数与精确检索完全相同，只是从并列副本中选中了另一个。实际检索质量无损。**

### 更深一层的发现：去重只做了一半

进一步定位重复来源，结果很精确：

| 角色 | 条目数 | 唯一 | 重复 |
|------|--------|------|------|
| user | 8317 | 8317 | **0** ✅ |
| assistant | 8317 | 6100 | **2217** ❌ |

**user 侧的去重是成功的，但 assistant 回复的模板重复没有被去掉**——2217 条重复全部来自 assistant 侧（重复最多的文本出现了 21 次）。第一轮实验声称"去重后 8317 条全部唯一"，那只保证了对话层面唯一，没覆盖到拆分后的 assistant 记忆条目。

**教训：数据去重必须覆盖到最终入库的每一条记录，而不是中间层。** 用 `diagnose_recall.py` 可随时复现这个诊断。

## 快速开始

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

> 需要 `faiss-cpu`。Windows / macOS / Linux 均可。

### 2. 配置 API

复制 `.env.example` 为 `.env`，填入你的 API 配置：

```bash
cp .env.example .env
```

```ini
OPENAI_API_KEY=sk-你的密钥
OPENAI_API_BASE=https://api.openai.com/v1   # 或你自己的 OpenAI 兼容网关
EMBEDDING_MODEL=text-embedding-3-small
VECTOR_DIM=1536                             # 必须与 embedding 模型输出维度一致
```

> `.env` 已在 `.gitignore` 中，不会进入仓库。

### 3. 三步跑通

```bash
python data_generator.py    # 1. 生成 1 万条模拟对话（固定随机种子，可复现）
python indexer.py           # 2. 批量 Embedding 入库（64 条/批）
python benchmark.py         # 3. NumPy / Flat / IVF 三引擎对比 + 100 条一致性验证
python hnsw_benchmark.py    # 4. IVF vs HNSW 对比（不调 API，复用已有向量）
```

> `hnsw_benchmark.py` 直接复用已生成的向量文件，不需要 API key，也不产生任何费用。

其他工具：

```bash
python search.py            # NumPy 检索 + 元数据过滤 + top-k 对比
python diagnose_recall.py   # 召回率差异诊断（并列分数分析）
python debug_ivf.py         # IVF bug 定位（打印原始分数）
```

## 踩过的坑

这份实验最值钱的不是性能数字，是下面这些坑——每一个都花了实际排查时间。

| 坑 | 现象 | 根因 | 教训 |
|----|------|------|------|
| **IVF 返回空结果** | 10 个查询 9 个空 | IVFFlat 默认用 L2 距离（越小越相似），代码却把分数当余弦相似度用（越大越相似），阈值过滤把正确结果全干掉了 | **FAISS 的 metric 不跟 quantizer 走**，IVF / HNSW 都必须显式指定 `METRIC_INNER_PRODUCT` |
| **IVF 参数优化不足** | 2K 时 IVF 和 Flat 差不多 | `nprobe=nlist//2` 扫了 50% 聚类，省不了多少 | 大规模必须降 nprobe 比例（本项目降到 12%），否则 IVF 没意义 |
| **数据重复率 94%** | 100 条随机验证 top-1 一致率只有 6% | 变量池太小，1 万条只有 582 条唯一；IVF 和 NumPy 找到的是分数相同的不同副本 | 生成时去重 + 扩大变量池，去重后一致率 100% |
| **去重只做了一半** | HNSW 召回率卡在 98.8%，扫参数无效 | user 侧去了重，**assistant 侧模板重复没去**（2217 条重复）；近似索引与精确索引从并列副本里选了不同条目 | **去重必须覆盖最终入库的每一条记录**，不是中间层 |
| **误读召回率** | 以为 HNSW 精度不如 IVF | 分数差异仅 1e-7（浮点误差），15/200 条分数集合完全相同 | 评测近似检索时**必须同时看分数**，只看 ID 会把并列分数误判成精度损失 |
| **单次计时噪声大** | nprobe=1 比 nprobe=2 还慢，曲线不单调 | 单次计时受系统调度干扰 | 每条查询重复多次取中位数，性能曲线才可信 |
| **验证样本太少** | 10 条手写查询 10/10，以为没问题 | 手写查询是 paraphrase，不在库内，没暴露重复问题 | 验证必须包含**库内随机抽样**，且数据需去重 |
| **JSON 文件过大** | 2 万条全 JSON 预计 400MB+ | 每个浮点数以 18 字符文本存储 | embedding 改存 `.npy` 二进制，省 80% 空间 |
| **json.dump 参数写反** | 存储时报 TypeError | 第一个参数应该是数据不是文件对象 | 低级错误，但程序崩了重来要重新调 API（浪费钱） |
| **JSON 文件损坏** | 加载时报 JSONDecodeError | 上次写入失败留了坏文件 | load 加 try-except 容错 |

## 设计要点

- **批量 Embedding**：64 条/批调 API，2 万条只需 312 次调用（逐条要 2 万次），耗时 191 秒
- **两级存储**：元数据存 JSON（可读、可过滤），embedding 存 `.npy`（紧凑、读写快）
- **元数据过滤**：每条记忆带 `topic` 和 `timestamp`，支持按主题检索
- **IVF 参数**：`nlist = n/100`（上限 1024），`nprobe = nlist/8`（扫 12% 聚类）
- **HNSW 参数**：`M=32`（邻居数）、`efConstruction=200`（建图宽度）、`efSearch=64`（查询宽度）
- **无 API 依赖的对比实验**：`hnsw_benchmark.py` 复用已有向量文件，可离线复现
- **可复现**：数据生成固定随机种子（`random.seed(42)`），验证抽样也固定种子
